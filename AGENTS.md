# MagicRPG и Codex

## Сборка

- Целевая платформа — Minecraft 26.3 и Java 25. Используй Gradle Wrapper. Версия NeoForge для разработки задана в `gradle.properties`.
- Запускай команды из корня проекта. Выбор JDK, локальных зависимостей и каталоги запуска описаны в [README.md](README.md).
- При каждом изменении кода или игровых ресурсов повышай версию MagicRPG в поле `version` файла `build.gradle` перед сборкой.
- После изменения кода или ресурсов собери JAR без запуска тестов: `.\gradlew.bat build -x test` на Windows или `./gradlew build -x test` в POSIX-оболочке. Готовый JAR лежит в `build/libs/`.

## Карта проекта

- `src/main/java/io/github/magicrpg/MagicRpg.java` — точка входа и регистрация контента.
- `compat/reforged/` внутри Java-пакета — все прямые вызовы API Reforged. Для обсуждения механик и проверки API сначала используй код, [справочник API](docs/minecraft-api.md) и локальный JAR Reforged 1.1.3 для 26.3. К исходникам тега `26.3` обращайся, если локальных данных недостаточно.
- `client/` внутри Java-пакета — модели, рендереры и клиентская регистрация. Общий код должен запускаться на выделенном сервере.
- `src/main/resources/assets/magicrpg/` — модели предметов, текстуры и локализации `en_us` и `ru_ru`. `src/main/resources/data/magicrpg/` — игровые данные с пространством имён `magicrpg`.

## README и Таумономикон

- Размещай все исследования MagicRPG во вкладке «Чудовищные твари» (`MAGICRPG_BEASTS`).
- Обугленный клык открывает входы в измерения MagicRPG. В Таумономиконе исследование входа в каждое измерение, включая будущие, должно иметь видимую связь и прямое требование к исследованию «Обугленный клык» (`MAGICRPG_CHARRED_FANG`). Лиловые луга и Златолесье — независимые ветки. Путевые зеркала относятся к ветке Лугов.
- Регистрируй все предметы MagicRPG, включая предметы-блоки, в отдельном разделе творческого инвентаря MagicRPG.
- В игровом описании в `README.md` кратко знакомь читателя с биомами, обитателями и другими особенностями мода. Заинтересуй читателя и оставь рецепты, условия и инструкции для Таумономикона.
- Для каждой новой или изменённой игровой возможности добавляй или обновляй запись в Таумономиконе. Игроку должно быть понятно, как воспользоваться находкой. Вплетай в рассказ точные материалы, действия и условия, от которых зависит результат.
- Пиши в обеих локализациях от первого лица, как тауматург, который ведёт дневник исследований. Начинай с наблюдения, догадки или опыта и через результат объясняй, что можно сделать. Обычно достаточно одного-двух коротких абзацев. Называй предметы и явления так, как их назвал бы герой в игровом мире.

## Разработка и передача на проверку

- Codex пишет код и игровые ресурсы. Пользователь проводит проверки сам. Codex запускает тесты, игровой клиент, сервер или сценарии проверки только по прямой просьбе пользователя.
- Назначай каждому новому предмету MagicRPG собственные аспекты Reforged, включая предметы, которые представляют блоки. Включай в инструкции проверку сканирования таумометром и сохранения результатов в знаниях игрока.
- Сохраняй существующие идентификаторы контента и ключи исследований. При добавлении контента обновляй обе локализации.
- Для призыва, расхода предметов и переходов между измерениями описывай сценарии проверки на сервере. Если меняется состояние мира, добавляй шаги сохранения и повторной загрузки.
- Для игровых проверок указывай отдельный профиль и тестовый мир. Рабочий профиль и сохранения служат источником зависимостей. Для проверки совместимости указывай, какие моды и настройки нужно скопировать в отдельный профиль.
- Reforged — обязательная зависимость. TerraBlender нужен Reforged. Sodium и Horizon Iris используются только для клиентской проверки. Не включай сторонние JAR и локальные игровые данные в артефакт или Git.
- В итоговом ответе указывай результат сборки отдельно. Для каждого изменённого поведения давай список ручных проверок: подготовка, шаги и ожидаемый результат. Добавляй команды, координаты или идентификаторы, когда они упрощают воспроизведение.
