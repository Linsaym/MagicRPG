# Создание босса и расширение API

1. Опиши арену, участников и сценарий по тикам. Для каждой атаки зафиксируй подготовку, момент фиксации направления, удар, восстановление и условия прерывания.
2. Создай сущность на базе `BossMob` и зарегистрируй её тип, атрибуты, цели ИИ и клиентский рендерер по обычным правилам MagicRPG. Помести общие для сервера и рендерера ID и времена в доступные обоим константы.
3. Объяви способности и фазы. Переиспользуй `BossZone`, `BossActions` и временные ресурсы из `BossContext`. Для особых действий босса используй типизированный `BossAction<ИмяБосса>`.
4. Свяжи клипы с моделью по [руководству анимации](animation.md). Зарегистрируй и проверь модель, текстуру и игровые описания по правилам проекта.
5. Добавь сценарии GameTest для нового поведения. При игровой проверке проверь уклонение на границе зоны, две цели, прерывание на подготовке, потерю цели, повторный заход в арену и визуальное совпадение ключевого кадра удара с эффектом.

Общие правила `BossMob` возвращают босса после смерти и ограничивают полёт участников активного боя. Для защиты от полёта движок использует тот же фильтр `canHit`, что и зональные атаки. При выборе исходной точки учитывай площадку под боссом и объём, который он освобождает при возвращении.

В сущности достаточно такого подключения. Способности `CLEAVE` и `WAVE` даны в [примерах](examples.md).

```java
private static final BossEncounter<ExampleBoss> ENCOUNTER = new BossEncounter<>(List.of(
    new BossEncounter.Phase<>(MagicRpg.id("example_frenzy"),
        c -> c.boss().getHealth() <= c.boss().getMaxHealth() * .5F, List.of(WAVE, CLEAVE)),
    new BossEncounter.Phase<>(MagicRpg.id("example_opening"), List.of(CLEAVE))
));
private final BossFight<ExampleBoss> fight = new BossFight<>(this, ENCOUNTER);

@Override
protected BossFight<ExampleBoss> bossFight() {
    return fight;
}
```

Предикаты должны быть быстрыми и чистыми. Если ИИ ищет цели в области, ограничь область и частоту поиска. Для позиционных снимков и истории одного исполнения используй `BossContext.Key<T>`, для конфигурации — неизменяемые определения. Состояние босса и ресурсов используй на серверном потоке.

## Расширение движка

- Сначала проверь [справочник](api.md) и сценарии GameTest. Собери механику из готовых действий, если они уже дают нужное поведение.
- Добавляй переиспользуемые действия в `BossActions`, управление жизненным циклом и ресурсами — в `BossFight` и соответствующий внутренний класс. В коде босса оставляй его специфические цели, условия фаз, параметры и постановку способностей.
- Для нового действия определи момент применения, конфликт между несколькими исполнениями, предел нагрузки и очистку при завершении, прерывании, смерти и выгрузке. Проверяй границы чанков перед доступом к миру. Клиентские типы держи под `client/`.
- При изменении API обнови сигнатуры и примеры в документации и добавь проверку ключевого поведения в GameTest. При изменении смысла существующего вызова проверь его пользователей.

Запуск тестов из корня на Java 25.

```powershell
.\gradlew.bat runBossGameTest
```

Отчёт появится в `run/boss-game-test/report.xml`. Конфигурация запускает выделенный сервер Minecraft с временным тестовым миром в `run/boss-game-test/gametestserver`. Игровой JAR собирается отдельно командой `./gradlew build -x test` или `.\gradlew.bat build -x test`.
